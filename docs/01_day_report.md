## Принятые решения

### Роль вынесена в отдельный справочник `roles`

Если хранить название роли строкой в таблице `users`, возникает
транзитивная зависимость: название роли зависит от `role_id`, а не
от `user_id`. Это нарушает третью нормальную форму. При смене
названия роли пришлось бы обновлять все строки пользователей.
Справочник `roles` решает проблему: название хранится в одном
месте, а `users` ссылается через `role_id`.

### Цена хранится и в товаре, и в составе заказа

В таблице `products` цена актуальная — она может меняться.
В `order_items` фиксируется цена **на момент оформления заказа**.
Это нужно, чтобы при изменении цены в каталоге сумма уже
оформленных заказов осталась прежней. Историческая цена
сохраняется для корректного отображения прошлых заказов.

### Итоговая сумма заказа не хранится в базе

Сумма — производное значение: `SUM(quantity * price)` по позициям
заказа. Если хранить её отдельным полем, придётся обновлять его
при каждом изменении состава заказа, и возможны расхождения.
Сумма вычисляется при выборке через SQL-запрос с `SUM`.

### Товарная позиция — отдельная сущность `stock_items`

У одной модели много размеров, и для каждого размера своё
количество. Хранить размеры списком в строке товара нельзя —
это нарушение 1НФ (несколько значений в одной ячейке). Отдельная
таблица `stock_items` хранит по одной строке на каждую пару
`(модель, размер)` с полем `quantity`.

### Для размеров создан справочник `sizes`

Чтобы не дублировать значение размера (41, 42, 43) в каждой
товарной позиции, оно хранится один раз в `sizes`, а `stock_items`
ссылается через `size_id`. Это уменьшает объём данных и упрощает
обновление размерного ряда.

### Уникальные ограничения

- `users.login` — логин должен быть уникальным, потому что вход
  выполняется только по логину без пароля. Дубликат сделает
  невозможным однозначное определение пользователя.
- `roles.name` — названия ролей не должны повторяться.
- `sizes.value` — значение размера уникально.
- `(product_id, size_id)` в `stock_items` — одна модель одного
  размера встречается один раз.
- `(name, manufacturer)` в `products` — у одного производителя
  не может быть двух моделей с одинаковым названием.

### Ограничения целостности связей

Для связей выбраны два типа поведения при удалении:

- **ON DELETE CASCADE** — где дочерние записи не имеют смысла
  без родительской (заказ → позиции заказа, товар → товарные
  позиции).
- **ON DELETE RESTRICT** — где удаление нарушило бы историю или
  ссылочную целостность (нельзя удалить пользователя с заказами,
  роль с пользователями, товарную позицию, вошедшую в заказ).
