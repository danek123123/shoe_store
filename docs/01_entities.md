# Сущности и функциональные требования: «Чудо Обувь»

Первый артефакт проектирования. Документ содержит функциональные
требования и перечень основных сущностей предметной области.

## 1. Функциональные требования

1. В каталоге хранится актуальное доступное для заказа количество
   товарных позиций (сочетаний модели и размера).
2. Для каждой модели обуви в каталоге сохраняется изображение.
3. Пользователь выбирает из каталога одну или несколько пар обуви
   доступного размера и модели.
4. В интерфейсе доступен просмотр списка заказов с ключевой
   информацией: дата заказа, ФИО клиента.
5. Управление заказами: добавление, редактирование, удаление.

## 2. Роли пользователей

| Роль | Возможности |
|---|---|
| Неавторизованный | просмотр каталога (без фильтра, сортировки, поиска) |
| Авторизованный | каталог с фильтром/сортировкой/поиском, оформление заказа (добавить/удалить позиции, изменить количество) |
| Менеджер | всё, что авторизованный, плюс: просмотр заказов и состава, добавление и удаление заказов |
| Администратор | всё, что менеджер, плюс: редактирование заказов |

Вход выполняется только по логину из списка пользователей.
Пароль не требуется.

## 4. Связи между сущностями

- `subcategory` → `category` (многие к одному)
- `product` → `subcategory` (многие к одному)
- `product` → `manufacturer` (многие к одному)
- `product_item` → `product` (многие к одному)
- `product_item` → `size` (многие к одному)
- `order` → `user` (многие к одному)
- `order_item` → `order` (многие к одному)
- `order_item` → `product_item` (многие к одному)

## 5. Бизнес-правила

- Количество товарной позиции не может быть отрицательным.
- Цена — положительное число.
- Размер обуви — от 16 до 50.
- Итоговая сумма заказа = сумма по всем позициям.
- Вход выполняется только по логину из таблицы `user`.

## 7. Аутентификация: вход по логину

Вход в систему выполняется **только по логину**, без пароля. Логин
выбирается пользователем из заранее заданного списка.

### 7.1. Требование к уникальности

Поле `login` в таблице `user` должно быть **уникальным**. Это
обеспечивает однозначное определение пользователя при входе.

### 7.2. Что произойдёт при дублировании логина

Если два пользователя получат одинаковый логин:

- система не сможет однозначно определить, кто именно вошёл;
- права доступа могут быть по ошибке повышены (например, обычный
  пользователь получит доступ менеджера);
- фильтрация заказов «мои заказы» и «заказы менеджера» будет
  работать некорректно.

### 7.3. Как предотвратить на уровне БД

- В определении таблицы `user` указать `login TEXT UNIQUE NOT NULL`.
- Это создаёт **уникальный индекс** на колонку `login`.
- При попытке вставить дубликат SQLite возвращает ошибку
  `UNIQUE constraint failed: user.login`.
- В коде `register_user` и подобных функциях нужно обрабатывать
  эту ошибку: либо отклонять регистрацию, либо сообщать пользователю,
  что логин занят.

Пример SQL:

    CREATE TABLE IF NOT EXISTS user (
        id INTEGER PRIMARY KEY AUTOINCREMENT,
        login TEXT NOT NULL UNIQUE,
        last_name TEXT NOT NULL,
        first_name TEXT NOT NULL,
        middle_name TEXT,
        role TEXT NOT NULL DEFAULT 'user'
    );

## 8. Данные товара для фильтрации, сортировки и поиска

Чтобы реализовать фильтрацию, сортировку и поиск в каталоге, таблица
товаров должна содержать соответствующие поля.

### 8.1. Что требуется для каждой операции

| Операция | Поля |
|---|---|
| Фильтрация | `category_id`, `subcategory_id`, `manufacturer_id`, `size` |
| Сортировка | `price`, `name` |
| Поиск | `name`, `manufacturer_id` (по названию производителя) |

### 8.2. Поля в таблицах

**В таблице `product`:**

- `name` — для поиска и сортировки по наименованию;
- `subcategory_id` — для фильтрации по категории и подкатегории;
- `manufacturer_id` — для поиска по производителю;
- `image_path` — изображение модели;
- `composition`, `description` — справочная информация.

**В таблице `product_item`:**

- `size_id` — для фильтрации по размеру;
- `price` — для сортировки по цене;
- `quantity` — для отображения доступного количества.

### 8.3. Индексы для ускорения

- индекс по `product(name)` — для поиска и сортировки по наименованию;
- индекс по `product(subcategory_id)` — для фильтрации по категории;
- индекс по `product(manufacturer_id)` — для поиска по производителю;
- индекс по `product_item(product_id, size_id)` — составной индекс
  для быстрого поиска товарной позиции;
- индекс по `product_item(price)` — для сортировки по цене.

Пример SQL:

    CREATE INDEX IF NOT EXISTS idx_product_name ON product(name);
    CREATE INDEX IF NOT EXISTS idx_product_subcategory ON product(subcategory_id);
    CREATE INDEX IF NOT EXISTS idx_product_manufacturer ON product(manufacturer_id);
    CREATE INDEX IF NOT EXISTS idx_item_product_size ON product_item(product_id, size_id);
    CREATE INDEX IF NOT EXISTS idx_item_price ON product_item(price);

### 8.4. Что это даёт

- Фильтрация по категории и подкатегории работает быстро благодаря
  индексу на `subcategory_id`.
- Сортировка по цене и наименованию — через индексы
  `idx_item_price` и `idx_product_name`.
- Поиск по наименованию и производителю — через индексы
  `idx_product_name` и `idx_product_manufacturer`.

## 9. Сущности и атрибуты

Сущности выделены из описания предметной области. Каждая сущность
снабжена первичным ключом по шаблону `<сущность>_id`. Для каждого
атрибута указано, обязательный ли он, уникальный ли, есть ли значение
по умолчанию.

Обозначения:

- **PK** — первичный ключ;
- **FK** — внешний ключ;
- **NOT NULL** — обязательное поле;
- **UNIQUE** — уникальное значение;
- **DEFAULT** — значение по умолчанию.

Справочник ролей. Вынесен в отдельную таблицу, чтобы не нарушать
третью нормальную форму.

|---|---|---|---|

## 10. Сводка ограничений

### 10.1. Обязательные (NOT NULL)

`login`, `last_name`, `first_name`, `role_id` у пользователя;
`name` у роли, категории, производителя, товара;
`value` у размера; `quantity`, `price` у товарной позиции;
`order_date`, `last_name`, `first_name`, `user_id` у заказа;
`order_id`, `item_id`, `quantity`, `price` у позиции заказа.

### 10.2. Необязательные (NULL)

`middle_name` у пользователя, `country` у производителя,
`image_path`, `composition`, `description` у товара,
`middle_name` у заказа.

### 10.3. Уникальные (UNIQUE)

- `user.login` — логин пользователя;
- `role.name` — название роли;
- `category.name` — название категории;
- `manufacturer.name` — название производителя;
- `size.value` — размер;
- `(product.name, product.manufacturer_id)` — модель + производитель;
- `(product_item.product_id, product_item.size_id)` — модель + размер.

### 10.4. Значения по умолчанию (DEFAULT)

- `product_item.quantity` = 0;
- `order.order_date` = текущая дата (`datetime('now')` в SQLite);
- `order.status` = `'new'`;
- `order.total` = 0;
- `user.role_id` — по умолчанию можно указать `user` (обычная роль).

## 11. Связи между сущностями

Для каждой связи указан тип (1:1, 1:N, M:N) и ограничения
целостности.

### 11.1. Список связей

| № | Связь | Таблицы | Тип | Ограничение |
|---|---|---|---|---|
| 1 | Пользователь → Заказ | `user` → `order` | 1:N | ON DELETE RESTRICT |
| 2 | Роль → Пользователь | `role` → `user` | 1:N | ON DELETE RESTRICT |
| 3 | Категория → Подкатегория | `category` → `subcategory` | 1:N | ON DELETE CASCADE |
| 4 | Подкатегория → Товар | `subcategory` → `product` | 1:N | ON DELETE RESTRICT |
| 5 | Производитель → Товар | `manufacturer` → `product` | 1:N | ON DELETE RESTRICT |
| 6 | Товар → Товарная позиция | `product` → `product_item` | 1:N | ON DELETE CASCADE |
| 7 | Размер → Товарная позиция | `size` → `product_item` | 1:N | ON DELETE RESTRICT |
| 8 | Заказ → Позиция заказа | `order` → `order_item` | 1:N | ON DELETE CASCADE |
| 9 | Товарная позиция → Позиция заказа | `product_item` → `order_item` | 1:N | ON DELETE RESTRICT |

**Пояснение по типам:**

- **1:N (один-ко-многим):** у одной записи в левой таблице может быть
  много записей в правой. Например, один пользователь оформляет много
  заказов.
- Связь «Товар ↔ Размер» — **M:N** (многие-ко-многим). Разрешается
  через промежуточную таблицу `product_item`. В явном виде M:N-связей
  в схеме нет — все разрешены через промежуточные таблицы.

### 11.2. Почему товарная позиция — отдельная сущность

Товарная позиция — это **сочетание модели и размера**. Она выделена
в отдельную таблицу `product_item` по трём причинам.

**1. Требование 1НФ (атомарность).** Если хранить размеры и их
количество прямо в строке товара, получится несколько значений в одной
ячейке. Пример нарушения:

| product_id | name | sizes_and_quantity |
|---|---|---|
| 1 | Кроссовки Nike | 40:5, 41:3, 42:0 |

Здесь в колонке `sizes_and_quantity` — список, а не одно значение.
Это нарушение первой нормальной формы.

**2. У каждого размера своё количество.** Модель 41-го размера может
быть в наличии 3 пары, а 42-го — 0. Если хранить размеры в одной
строке, невозможно нормально обновлять остатки.

**3. Цена и количество зависят именно от пары (модель, размер).**
Это классический признак отдельной сущности — составного ключа
`(product_id, size_id)`.

### 11.3. Ограничения целостности

- **ON DELETE CASCADE** — при удалении родительской записи
  автоматически удаляются все дочерние.
  - Удаляем заказ → удаляются все его позиции.
  - Удаляем товар → удаляются все его товарные позиции.
  - Удаляем категорию → удаляются её подкатегории.

- **ON DELETE RESTRICT** — запрет удаления, если на запись
  ссылаются другие таблицы.
  - Нельзя удалить пользователя, если у него есть заказы.
  - Нельзя удалить роль, если есть пользователи с этой ролью.
  - Нельзя удалить производителя, если у него есть товары.
  - Нельзя удалить размер, если на него ссылаются товарные позиции.
  - Нельзя удалить товарную позицию, если она вошла в состав заказа
    (`order_item`). Иначе в заказе останется «битая» ссылка.

### 11.4. Таблица связей (сводно)

| Таблица A | Таблица B | Тип | ON DELETE |
|---|---|---|---|
| role | user | 1:N | RESTRICT |
| user | order | 1:N | RESTRICT |
| category | subcategory | 1:N | CASCADE |
| subcategory | product | 1:N | RESTRICT |
| manufacturer | product | 1:N | RESTRICT |
| product | product_item | 1:N | CASCADE |
| size | product_item | 1:N | RESTRICT |
| order | order_item | 1:N | CASCADE |
| product_item | order_item | 1:N | RESTRICT |
