# Вопросы для самопроверки

Вопросы и краткие ответы по материалу проектирования БД
для предметной области «Чудо Обувь».

**1. Почему товарная позиция — отдельная сущность?**

У одной модели много размеров, и для каждого размера своё
количество на складе. Если хранить размеры списком в строке
товара, нарушается 1НФ (несколько значений в одной ячейке).
Отдельная таблица `stock_items` решает это: одна строка — одна
пара (модель, размер) со своим количеством.

**2. Почему роль вынесена в справочник?**

Если хранить роль строкой в `users`, возникнет транзитивная
зависимость: название роли зависит от роли, а не от пользователя.
Это нарушение 3НФ. Справочник `roles` + поле `role_id` в `users`
устраняют эту проблему.

**3. Почему цена хранится и в товаре, и в составе заказа?**

В `products` цена актуальная — она может меняться. В `order_items`
цена фиксируется на момент оформления заказа. Иначе при изменении
цены в каталоге изменилась бы и сумма уже оформленных заказов.
Историческая цена должна сохраняться.

**4. Почему итоговая сумма заказа не хранится в базе?**

Сумма — производное значение: `SUM(quantity * price)`
по `order_items`. Хранить её отдельно — значит дублировать
данные и рисковать расхождением при изменении позиций. Сумма
вычисляется при выборке.

**5. Что произойдёт, если удалить товар, который уже вошёл
в заказ?**

Если у внешнего ключа стоит `ON DELETE RESTRICT` — удаление
запрещено, пока есть ссылки из `order_items`. Если `ON DELETE
CASCADE` — удалятся и позиции заказа, что исказит историю.
Для товаров из каталога правильнее `RESTRICT`.

**6. Что произойдёт, если два пользователя получат одинаковый
логин?**

Система не сможет однозначно определить, кто вошёл; возможны
ошибки прав доступа. Предотвращается ограничением
`UNIQUE` на поле `login`. При попытке вставить дубликат
SQLite вернёт ошибку `UNIQUE constraint failed`.

**7. Как схема защищает от аномалии обновления?**

Данные не дублируются. Фамилия клиента хранится в одном месте —
в таблице `users`. При смене фамилии обновляется одна строка,
и все заказы автоматически видят новое значение через JOIN.

**8. Какие ограничения целостности нужны на каждой связи?**

- `roles → users`: `ON DELETE RESTRICT` (нельзя удалить роль,
  пока у неё есть пользователи).
- `users → orders`: `ON DELETE RESTRICT` (нельзя удалить
  пользователя с заказами).
- `products → stock_items`: `ON DELETE CASCADE`.
- `sizes → stock_items`: `ON DELETE RESTRICT`.
- `orders → order_items`: `ON DELETE CASCADE`.
- `stock_items → order_items`: `ON DELETE RESTRICT`.

**9. Почему в описании товара хранятся и категория,
и подкатегория?**

В упрощённой схеме из методички они хранятся текстом для
удобства фильтрации. В полной 3НФ-схеме их выносят
в отдельные справочники `category` и `subcategory`, а в `products`
хранят только ссылки.

**10. Зачем нужен отдельный справочник `sizes`?**

Чтобы избежать дублирования значений размера в каждой товарной
позиции. В `stock_items` хранится ссылка `size_id`, а само число
(41, 42, 43) — в одном месте. Это уменьшает объём и упрощает
обновление.
