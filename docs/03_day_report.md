## 3. Принятые решения

### 3.1. Имена

Все имена таблиц и полей были проверены по правилам:

- начинаются с буквы;
- только строчные латинские буквы, цифры и `_`;
- нижний регистр;
- не зарезервированные слова SQL;
- таблицы — во множественном числе;
- поля — в единственном числе;
- идентификаторы — с суффиксом `_id`.

**Исправлений не потребовалось** — исходная схема из дня 2 уже
соответствовала правилам. Исключение составила лишь пара «value»
в списке зарезервированных слов в скрипте проверки: в SQLite
`value` зарезервированным не является, поэтому оно было убрано
из списка. Имя поля `sizes.value` оставлено без изменений.

### 3.2. Ограничения CHECK

Добавлены следующие ограничения:

| Таблица | Поле | CHECK | Зачем |
|---|---|---|---|
| products | name | length(name) > 0 | наименование не может быть пустым |
| products | price | price > 0 AND price < 1000000 | цена положительная и не чрезмерная |
| stock_items | quantity | quantity >= 0 | количество не может быть отрицательным |
| order_items | quantity | quantity > 0 | в заказе хотя бы одна единица |
| order_items | price | price > 0 | цена позиции положительная |
| users | login | length(login) >= 3 AND length(login) <= 20 | логин разумной длины |
| sizes | value | value > 20 AND value < 50 | размеры обуви в разумном диапазоне |
| orders | order_date | date(order_date) IS NOT NULL | корректный формат ISO 8601 |

### 3.3. Индексы

Создано десять индексов:

**По внешним ключам (ускоряют JOIN):**

- `idx_users_role_id` — users.role_id;
- `idx_orders_user_id` — orders.user_id;
- `idx_stock_items_product` — stock_items.product_id;
- `idx_stock_items_size` — stock_items.size_id;
- `idx_order_items_order` — order_items.order_id;
- `idx_order_items_item` — order_items.item_id.

**По полям поиска:**

- `idx_products_category` — фильтрация по категории;
- `idx_products_manufacturer` — поиск по производителю.

**По полям сортировки:**

- `idx_orders_order_date` — сортировка заказов по дате;
- `idx_products_price` — сортировка по цене.

Индексы **не создавались** на поля `description`, `composition`,
`image_path` — по ним не выполняется ни поиск, ни сортировка.
Это сохраняет баланс между скоростью выборки и скоростью
вставки.

### 3.4. Стратегии удаления внешних ключей

Для каждого внешнего ключа выбрана стратегия:

| Таблица | Поле | Ссылается на | ON DELETE | Почему |
|---|---|---|---|---|
| users | role_id | roles.role_id | RESTRICT | нельзя потерять пользователей при удалении роли |
| stock_items | product_id | products.product_id | RESTRICT | товар, вошедший в позиции, нельзя удалить |
| stock_items | size_id | sizes.size_id | RESTRICT | размер, используемый в позициях, нельзя удалить |
| orders | user_id | users.user_id | RESTRICT | нельзя удалить пользователя с заказами |
| order_items | order_id | orders.order_id | CASCADE | позиции не имеют смысла без заказа |
| order_items | item_id | stock_items.item_id | RESTRICT | нельзя потерять историческую цену заказа |

**RESTRICT** выбран там, где удаление родительской записи привело
бы к потере важных данных или нарушению ссылочной целостности.

**CASCADE** выбран только для связи `orders → order_items`, где
позиции — это часть заказа, и без заказа они не имеют смысла.

### 3.5. PRAGMA foreign_keys = ON

Включён в `get_connection()` — без него SQLite игнорирует FOREIGN
KEY. Это было проверено экспериментально: при попытке удалить
пользователя с заказами база возвращает `FOREIGN KEY constraint
failed`.
